## Abstract

This CHIP defines a protocol for silent payments on the Chia blockchain, adapted from Bitcoin's BIP-352. A silent payment is a payment to a static address without on-chain linkability or a need for any notifications. Version 0, defined here, covers XCH and CATs held in the standard Chia payment puzzle, and payments to a party to an offer. The protocol is specified for XCH first and then extended to CATs, including revocable CATs.

## Motivation

When a user publishes a regular XCH address, every payment to that address is easily linkable by any observer. Generating a fresh address for each payer requires interaction, which is impractical for donations, invoices, or public profiles.

Silent payments allow the sender to derive a fresh, unlinkable address from the recipient's static address — without interaction, without extra on-chain data, and without any visible difference from a normal transaction.  The recipient will generate a static silent payment address once.  After publishing it, the recipient will need to scan all coin spends on the blockchain to see if the static address was the destination of a payment. 

### Comparison with BIP-352

Bitcoin's BIP-352 (Silent Payments, authored by josibake, Ruben Somsen, and Sebastian Falbesoner) defines a silent payment protocol for Bitcoin using ECDH on secp256k1. The sender's input public keys, visible in transaction witnesses, serve as the sender's contribution to the ECDH. This CHIP adapts that approach to the Chia blockchain's BLS12-381 cryptography and coin set model, using the synthetic public key from the standard puzzle reveal in place of Bitcoin's input keys.

Key differences from BIP-352:

| | BIP-352 | This CHIP |
|---|---|---|
| Curve | secp256k1 | BLS12-381 |
| Sender key source | Transaction input witness | Standard puzzle reveal (synthetic public key) |
| Key derivation | BIP-32, hardened | EIP-2333 (hardened) |
| Address format | `sp1q...` (bech32m, 66 bytes) | `spxch1q...` (bech32m, 96 bytes) |
| Input hash | hash(smallest outpoint \|\| *A*) | hash(smallest coin ID \|\| *A*) |
| Transaction inputs | Explicit in the transaction | Inferred spend group (`ASSERT_CONCURRENT_SPEND` cycle) |
| Hash to scalar | Fail if the hash is 0 or not below the group order | Reduce mod *r*; fail only if the result is 0 |
| Shared secret | Serialized ECDH point is hashed directly into *t*<sub>k</sub> | ECDH point is first hashed to a 32-byte *shared_secret* |
| Labels | Point subtraction on output keys | Forward computation on puzzle hashes |

## Goals

The aim of this protocol is to satisfy the following properties, taken from BIP-352:

* No increase in the size or cost of transactions
* Resulting transactions are indistinguishable from standard Chia blockchain spends and cannot be identified as silent payments
* Transactions cannot be linked to a silent payment address by an outside observer
* No sender-receiver interaction required
* No linking of multiple payments to the same sender
* Each silent payment goes to a unique address, avoiding accidental address reuse
* Supports payment labeling
* Uses existing mnemonic seed phrase and BLS key derivation for backup and recovery
* Separates scanning and spending responsibilities
* Compatible with multi-input spends (aggregated key transactions)
* Protocol is upgradeable

## Overview

This overview is taken from BIP-352, modified with details for this CHIP. In what follows:

- Uppercase letters represent public keys
- Lowercase letters represent private keys
- || refers to byte concatenation
- · refers to elliptic curve scalar multiplication on BLS12-381 G1
- *G* represents the generator point and *r* represents the group order

Each section builds on the previous one to introduce a different aspect of the protocol. For the full specification, see [Specification](#specification).

**Simple case**

Bob publishes a public key *B* as a silent payment address. Alice selects a coin with synthetic secret key *a*, public key *A*, and creates a destination output for Bob:

* Let *P* = *B* + hash(*a* · *B*) · *G*
* Encode *P* as a standard `p2_delegated_puzzle_or_hidden_puzzle` puzzle hash

Since *a* · *B* == *b* · *A* ([Elliptic-curve Diffie-Hellman](https://en.wikipedia.org/wiki/Elliptic-curve_Diffie%E2%80%93Hellman)), Bob can scan with his private key *b*. For each spent coin in a block, he extracts the synthetic public key *A* from the puzzle reveal and calculates *P* = *B* + hash(*b* · *A*) · *G*. If *P*'s puzzle hash matches one of the new coins in the block, that coin is a silent payment to Bob.

**Creating more than one output**

To allow Alice to create more than one output for Bob, an integer counter is included:

* Let *k* = 0
* Let *P*<sub>0</sub> = *B* + hash(*a* · *B* || *k*) · *G*
* For additional outputs:
  * Increment *k* by one
  * Let *P*<sub>k</sub> = *B* + hash(*a* · *B* || *k*) · *G*

Bob detects this output the same as before by searching for *P*<sub>0</sub> = *B* + hash(*b* · *A* || 0) · *G*. Once he detects the first output, he must:

* Check for *P*<sub>1</sub> = *B* + hash(*b* · *A* || 1) · *G*
* If *P*<sub>1</sub> is not found, stop
* If *P*<sub>1</sub> is found, continue to check for *P*<sub>2</sub> and so on until an additional output is not found

Since Bob will only perform these subsequent checks after finding at least one matching output, the increase to his overall scanning requirement is negligible.

**Preventing address reuse**

If Alice were to spend a different coin with the same synthetic public key *A*, she would derive the same destinations. To prevent this, Alice includes an input hash:

* Let *input_hash* = hash(*coin_id* || *A*)
* Let *P*<sub>0</sub> = *B* + hash(*input_hash* · *a* · *B* || 0) · *G*

The coin ID is unique per coin (derived from parent info, puzzle hash, and amount), so even if Alice reuses the same key, each transaction produces different one-time addresses. Bob must calculate the same *input_hash* when scanning.

**Using all inputs**

In the simplified example above, Alice's transaction has only one input *A*, but a Chia spend bundle can spend many coins. Rather than picking one input, Alice sums all her input secret keys:

* Let *a* = *a*<sub>1</sub> + *a*<sub>2</sub> + ... + *a*<sub>n</sub>
* Let *input_hash* = hash(*coin_id*<sub>L</sub> || (*a* · *G*)), where *coin_id*<sub>L</sub> is the lexicographically smallest coin ID
* Let *P*<sub>0</sub> = *B* + hash(*input_hash* · *a* · *B* || 0) · *G*

This reduces Bob's scanning cost. Instead of checking each input separately, Bob sums the synthetic public keys extracted from each coin's puzzle reveal and performs one ECDH per spend group.

**Scan and spend key**

Since Bob needs his private key *b* to check for incoming payments, *b* must be exposed to an online device. To minimize risk, Bob publishes an address of the form (*B*<sub>scan</sub>, *B*<sub>spend</sub>). He keeps *b*<sub>spend</sub> in offline cold storage and scans with *b*<sub>scan</sub> and *B*<sub>spend</sub>. Alice performs the tweak using both of Bob's public keys:

* Let *P*<sub>0</sub> = *B*<sub>spend</sub> + hash(*input_hash* · *a* · *B*<sub>scan</sub> || 0) · *G*

Bob detects this payment by calculating *P*<sub>0</sub> = *B*<sub>spend</sub> + hash(*input_hash* · *b*<sub>scan</sub> · *A* || 0) · *G* with his online device and can spend using (*b*<sub>spend</sub> + hash(*input_hash* · *b*<sub>scan</sub> · *A* || 0)) mod *r* as the private key.

**Labels**

For a single silent payment address of the form (*B*<sub>scan</sub>, *B*<sub>spend</sub>), Bob may wish to differentiate incoming payments. Bob could publish multiple silent payment addresses, but this would require him to scan for each one, which becomes prohibitively expensive. Instead, Bob can label his spend public key *B*<sub>spend</sub> with an integer *m*:

* Let *B*<sub>m</sub> = *B*<sub>spend</sub> + hash(*b*<sub>scan</sub> || *m*) · *G* where *m* is an incrementable integer starting from 1
* Publish (*B*<sub>scan</sub>, *B*<sub>1</sub>), (*B*<sub>scan</sub>, *B*<sub>2</sub>) etc.

Alice performs the tweak as before using one of the published (*B*<sub>scan</sub>, *B*<sub>m</sub>) pairs. Bob detects the labeled payment in the following manner:

* Let *P*<sub>0</sub> = *B*<sub>spend</sub> + hash(*input_hash* · *b*<sub>scan</sub> · *A* || 0) · *G*
* For each output puzzle hash, compute *P*<sub>0</sub> + *label_pk* for each registered label and compare the resulting puzzle hash against the output

Unlike BIP-352, which uses point subtraction on output public keys, Chia must use forward computation because outputs are identified by puzzle hashes (not public keys). Point subtraction on puzzle hashes is mathematically undefined, so the scanner computes forward from each candidate label.

It is important to note that an outside observer can easily deduce that each published (*B*<sub>scan</sub>, *B*<sub>m</sub>) pair is owned by the same entity, since each address shares the same *B*<sub>scan</sub>. Labels are not meant as a way for Bob to manage separate identities, but rather a way to distinguish payment sources.

**Labels for change**

Bob can also use labels for managing his own change outputs. The index *m* = 0 is reserved for this use case. This gives Bob an alternative to using BLS key derivation for managing change, while still allowing him to know which of his unspent outputs were change when recovering his wallet from the mnemonic. It is important that the wallet never hands out the label with *m* = 0 in order to ensure nobody else can create payments that are wrongly labeled as change.

While the use of labels is optional, every receiving silent payments wallet should at least scan for the change label when recovering from backup in order to ensure maximum cross-compatibility.

## Backwards Compatibility

This proposal is fully backwards compatible. Silent payment coins are ordinary Chia coins held in the standard puzzle `p2_delegated_puzzle_or_hidden_puzzle`, bare for XCH or inside the CAT layers for a CAT, and a silent payment adds no data on chain. No changes to the consensus layer, the standard puzzle, the CAT puzzles, or the network protocol are required.

Wallets that do not implement this CHIP will not be able to use this protocol and will not detect or send silent payment coins.

## Rationale

This CHIP adapts BIP-352, a silent payment protocol designed for Bitcoin, to the Chia blockchain. The basic design — using ECDH to derive unlinkable one-time addresses from a static recipient public key — translates directly. The key adaptations for Chia blockchain are:

- **Sender key source:** Bitcoin extracts the sender's public key from transaction input witnesses. Chia extracts it from the standard puzzle reveal, where the synthetic public key is curried into `p2_delegated_puzzle_or_hidden_puzzle`. This key is always available on-chain for any standard spend.
- **Key derivation:** Like BIP-352, this CHIP requires hardened derivation for the scan and spend keys, so that a leaked scan key cannot compromise the wallet: with unhardened derivation, a child secret key together with its parent's public key reveals the parent's secret key. Purpose indices 12 and 13 avoid the indices Chia already uses.
- **Hash to scalar:** BIP-352 fails when a hash is not below the group order, which for secp256k1 essentially never happens. The BLS12-381 group order *r* is roughly 2<sup>255</sup>, so the same rule would reject more than half of all SHA-256 outputs. This CHIP reduces the hash mod *r* instead. The resulting bias is under one bit and does not affect the protocol's security.
- **Label detection:** Bitcoin outputs are public keys, so labels can be detected by point subtraction. Chia outputs are puzzle hashes, so point subtraction is undefined. The scanner uses forward computation instead — deriving the puzzle hash for each candidate label and comparing against outputs. This makes scanning cost grow with the number of labels (see Scanning Cost of Labels).
- **Multi-input grouping:** Unlike a Bitcoin transaction, a Chia block merges all spend bundles, so sender and scanner must agree from on-chain data alone which spends form one transaction. Senders bind their input coins in a cycle of `ASSERT_CONCURRENT_SPEND` conditions ([CHIP-0014](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0014.md)), and scanners recover the group as a strongly connected component (see Inputs for Shared Secret Derivation). Grouping by shared puzzle hash, by coin-announcement linkage or by message conditions ([CHIP-0025](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0025.md)) was considered and rejected.
- **CATs:** Wallets hold CATs under the same standard puzzle as XCH and spend them in the same transactions, so version 0 covers CATs, including revocable CATs, as well as XCH (see Extension to CATs).
- **Coins that are not eligible do not bind:** A coin that is not an eligible spend adds no vertex and no edge to the concurrent-spend graph, even when it lies on a cycle between eligible coins. The conditions of such a coin need not be committed to by the payer's signature (an offer's settlement coin can be spent by anyone), so a third party could use one to join or split a group.
- **Closed list of eligible spends:** Every sender and scanner must agree on which spends contribute a key. A new kind of eligible spend changes the key sum, and so the spend groups and tweak points, of every transaction that contains one, so once this CHIP is Final the eligible spends of an address version form a closed list and a new kind of eligible spend needs a new address version (see Future Extensions).
- **Address encoding:** The silent payment address encodes two 48-byte BLS G1 public keys (scan + spend) in a bech32m string with prefix `spxch` (mainnet) or `tspxch` (testnet), following Chia's `xch`/`txch` convention. A leading version character mirrors BIP-352's address versioning and provides the protocol's upgrade path (see Address Versioning).
- **ECDH rather than pairings:** BLS12-381 supports bilinear pairings, which could enable alternative shared secret constructions (for example, deriving the shared secret from the on-chain BLS signature). ECDH via scalar multiplication on G1 is simpler, well understood, and sufficient for the purpose.

A recorded community discussion of this CHIP is linked from the Comments-URI.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

### Scope of Version 0

Version 0 of this protocol covers XCH and CATs, including revocable CATs, held in the standard puzzle, and payments through settlement coins:

- **Inputs:** A coin contributes to a silent payment when its spend is an eligible spend (see Eligible CAT Spends): the standard puzzle bare, inside `cat_v2`, or inside `cat_v2` and the revocation layer on the holder's path. XCH and CAT coins spent in one `ASSERT_CONCURRENT_SPEND` cycle form one spend group (see Inputs for Shared Secret Derivation). Coins of any other kind — NFTs, DIDs, singletons, vaults, fee CATs, settlement coins — are not eligible and, inside a cycle, add no vertex and no edge.
- **Outputs:** A silent payment output is a coin of the standard puzzle with a one-time key, bare for XCH or under the wrapper of its asset for a CAT, created by a coin of that asset in the sender's spend group or by a settlement coin. A CAT coin created by a coin that is not a CAT (a mint) is not covered.

A party to an offer can be paid at a silent payment address (see Payments through Settlement Coins).

The Specification first defines the protocol for XCH, from Definitions to Edge Cases. Extension to CATs then extends it to CATs, and Payments through Settlement Coins covers payments through an offer. The extension is part of version 0, not an option (see Extension to CATs).

### Definitions

- **`G1`**: The G1 group of the BLS12-381 curve.
- ***G***: The generator point of G1.
- ***r***: The order of the G1 group: `0x73EDA753299D7D483339D80809A1D80553BDA402FFFE5BFEFFFFFFFF00000001`.
- **serialize(*P*)**: The 48-byte compressed representation of a G1 point *P*.
- **ser<sub>32</sub>(*k*)**: The 4-byte big-endian serialization of a 32-bit integer *k*.
- **ser<sub>256</sub>(*x*)**: The 32-byte big-endian serialization of a 256-bit scalar *x* (private key).
- **tagged_hash(*tag*, *data*)**: SHA256(SHA256(*tag*) || SHA256(*tag*) || *data*) — BIP-340-style tagged hash for domain separation. The *tag* is a UTF-8 encoded string.
- **Recipient scan key pair**: (*b*<sub>scan</sub>, *B*<sub>scan</sub>). Used for ECDH detection. See Key Derivation.
- **Recipient spend key pair**: (*b*<sub>spend</sub>, *B*<sub>spend</sub>). Used for spending detected coins. See Key Derivation.
- **Silent payment address**: The pair (*B*<sub>scan</sub>, *B*<sub>spend</sub>), encoded as a bech32m string.
- **Labeled address**: (*B*<sub>scan</sub>, *B*<sub>m</sub>) where *B*<sub>m</sub> = *B*<sub>spend</sub> + *label_pk* for label index *m*.
- **Standard puzzle**: `p2_delegated_puzzle_or_hidden_puzzle` curried with a single synthetic public key (see Recognizing an Eligible Spend).
- **Eligible spend**: A coin spend whose puzzle reveal is the standard puzzle (see Recognizing an Eligible Spend). Its key is the synthetic public key of that standard puzzle, and its coin ID is the spent coin's own. The Extension to CATs adds two kinds of eligible spend, and no other spend is eligible in version 0 (see Extension to CATs). The kind of coin being spent does not matter: a farming reward coin held in the standard puzzle is an eligible spend when it is spent.
- **Sender synthetic key pair**: (*a*<sub>syn</sub>, *A*<sub>syn</sub>) where *a*<sub>syn</sub> is the sender's synthetic secret key and *A*<sub>syn</sub> is the synthetic public key curried into the sender's standard puzzle.
- **Coin ID**: SHA256(parent_coin_info || puzzle_hash || amount) — Chia's unique identifier for a coin.
- **Spend group**: The set of eligible spends that serves as the input set of one silent payment transaction: either a single eligible spend, or two or more eligible spends bound into a cycle by `ASSERT_CONCURRENT_SPEND` conditions. Defined precisely in Inputs for Shared Secret Derivation.
- ***n***: The number of coins in a spend group.
- ***A*<sub>sum</sub>**: The sum of the synthetic public keys of all coins in a spend group: *A*<sub>sum</sub> = *A*<sub>1</sub> + *A*<sub>2</sub> + ... + *A*<sub>n</sub>, with one term per coin even when several coins share a key.
- ***input_hash***: int(tagged_hash("Chia_SP/Inputs", *coin_id*<sub>L</sub> || serialize(*A*<sub>sum</sub>))) mod *r* where *coin_id*<sub>L</sub> is the lexicographically smallest coin ID in the spend group.
- **Tweak point**: *T* = *input_hash* · *A*<sub>sum</sub> for a spend group (see Tweak Points).
- **||**: Byte concatenation.
- ***O***: The identity element (point at infinity) of G1. serialize(*O*) = `0xc00000...00` (48 bytes with the compressed infinity flag set).
- Wrapper, wrap(*W*, *h*) and the wrapper list of a block are defined in Extension to CATs, and settlement coin in Payments through Settlement Coins.

- *G* is the generator point of the BLS12-381 G1 group; *r* is the group order.

### Silent Payment Address

The recipient's silent payment address encodes two public keys:
- *B*<sub>scan</sub>: the scan public key (48 bytes compressed G1)
- *B*<sub>spend</sub>: the spend public key (48 bytes compressed G1)

The address is encoded as a bech32m string with human-readable part `spxch` (mainnet) or `tspxch` (testnet). The data part is a single version character followed by the payload. For version 0, the payload is the 96-byte concatenation: serialize(*B*<sub>scan</sub>) || serialize(*B*<sub>spend</sub>).

For a labeled sub-address, *B*<sub>spend</sub> is replaced by *B*<sub>m</sub> = *B*<sub>spend</sub> + *label_pk* (see Labeling section). The scan key *B*<sub>scan</sub> is unchanged across all labels, so the sender always performs ECDH with the same scan key regardless of which label the address uses.

Decoders MUST reject an address unless both keys decode to valid elements of the prime-order G1 subgroup and neither is the identity element *O*. When the payload is converted from 5-bit to 8-bit groups, there MUST be at most four leftover padding bits, and they MUST be zero. As with any bech32m string, an address is written entirely in lower case or entirely in upper case; a mixed-case address is invalid. A sender SHOULD reject an address whose human-readable part does not match the network it is transacting on.

#### Address Versioning

The first 5-bit character of the data part (immediately after the `1` separator) encodes the address version, an integer from 0 to 31. Versioning follows BIP-352 and is this protocol's upgrade mechanism:

- **Version 0** is the format defined by this CHIP. Decoders MUST reject a v0 address whose payload is not exactly 96 bytes.
- **Versions 1 through 30** are reserved for forward-compatible upgrades. A sender that encounters an address with an unrecognized version in this range MUST NOT fail solely because the version is unknown: if the payload is at least 96 bytes, the sender MUST interpret the first 96 bytes as serialize(*B*<sub>scan</sub>) || serialize(*B*<sub>spend</sub>) and ignore any additional data. This allows future versions to append data to the payload without breaking existing senders. An address with a version in this range and a payload shorter than 96 bytes is invalid.
- **Version 31** is reserved for backward-incompatible upgrades. Senders MUST treat any version-31 address as invalid. A future breaking format change can use this version to force a wallet upgrade rather than risk mis-sent payments.

Silent payment addresses exceed the 90-character length limit that BIP-173 imposes on bech32 strings (a v0 `spxch` address is 167 characters). Following BIP-352, implementations MUST accept silent payment addresses up to 1,023 characters and MUST NOT enforce the 90-character limit on them (as in BIP-352, at a slight cost to the checksum's error-detection strength).

### Key Derivation

A wallet that derives its silent payment keys from a mnemonic MUST use [EIP-2333](https://eips.ethereum.org/EIPS/eip-2333) hardened derivation from the master secret key, at every level of these paths:

- Scan key: `m/12381n/8444n/12n/0n`
- Spend key: `m/12381n/8444n/13n/0n`

The `n` suffix marks a hardened derivation step. Wallets MUST NOT derive silent payment keys with Chia's unhardened derivation: an unhardened child secret key, combined with the parent public key, reveals the parent secret key.

Purpose indices 12 (scan) and 13 (spend) avoid the purpose indices Chia already uses. The final index 0 is reserved for future use as an account number.

The scan key is sufficient for payment detection (ECDH). The spend key is required to spend detected coins. This allows a "watch-only" scanner that holds only the scan key.

The rest of the protocol treats (*b*<sub>scan</sub>, *b*<sub>spend</sub>) as given: a key pair obtained in any other way produces valid addresses and payments, but will not be recoverable from a mnemonic by other wallets.

### Inputs for Shared Secret Derivation

Chia blocks contain no transaction boundaries: every spend bundle included in a block is merged into one list of coin spends. Sender and scanner must therefore agree, from on-chain data alone, on which coins form the input set of a silent payment. That set is the *spend group*.

**Concurrent-spend graph.** For a block, take the block's eligible spends as vertices. For each eligible spend *X*, and each `ASSERT_CONCURRENT_SPEND` condition (condition code 64, [CHIP-0014](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0014.md)) that *X* outputs naming a coin ID *Y*, add a directed edge *X* → *Y* if *Y* is also an eligible spend in the block. Only conditions that consensus itself treats as `ASSERT_CONCURRENT_SPEND` count; a scanner MUST NOT accept encodings of the condition code that consensus would not. The conditions of a spend are those output by running its full puzzle reveal with its solution, as consensus does. Conditions output by spends that are not eligible, and conditions naming coins that are not eligible spends in the block, add no edge. A coin that is not an eligible spend therefore adds no vertex and no edge, even when it lies on a cycle between eligible coins.

**Spend groups.** Every eligible spend on its own is a spend group (a *single-input group*). Every strongly connected component of size two or more in the concurrent-spend graph is also a spend group (a *multi-input group*).

Strongly connected components, not weakly connected ones, are required. A third party spending an unrelated coin in the same block can output a condition asserting a victim's coin ID, which creates a one-way edge into the victim's group. That spend is not in the victim's strongly connected component, because no coin in the group asserts it back.

The Extension to CATs makes CAT coins eligible spends and vertices of the same graph, so that one cycle can bind XCH and CAT coins into one spend group; every sender and scanner of version 0 MUST apply it (see Extension to CATs).

**Sender requirements.** A sender paying one or more silent payment addresses MUST satisfy all of the following:

1. **One cycle.** If more than one coin is to contribute to the payment, the sender MUST bind those coins into a single cycle: with the coins ordered *c*<sub>0</sub>, ..., *c*<sub>n-1</sub>, each coin *c*<sub>i</sub> outputs exactly one `ASSERT_CONCURRENT_SPEND` condition naming the coin ID of *c*<sub>(i-1) mod n</sub>. No other mechanism (coin announcements, message conditions) binds silent payment inputs. A payment funded by a single coin that is bound to no other eligible spend needs no such condition.
2. **Same set on both sides.** The sender MUST compute *a*<sub>sum</sub>, *A*<sub>sum</sub> and *coin_id*<sub>L</sub> over exactly the coins a scanner will find in the spend group: every eligible spend in the cycle, with one term per coin. This includes any coin that is both created and spent inside the transaction (an intermediate, or *ephemeral*, coin) if it is part of the cycle. The sender MUST hold the synthetic secret key of every coin in the group, and the cycle MUST NOT include an eligible spend whose key is left out of *a*<sub>sum</sub>.
3. **Use the multi-input group when there is one.** If the coin creating a silent payment output — or, for an output paid through a settlement coin, the coin asserting the settlement coin's puzzle announcement of it — is part of a cycle, the sender MUST derive the output from that multi-input group, not from the coin alone.
4. **Outputs come from the group.** Every silent payment output MUST be created by — that is, have as its parent — a coin in the spend group, or by a settlement coin whose puzzle announcement of that payment a coin of the group asserts (see Payments through Settlement Coins).
5. **Other coins stay outside.** Coins that are not eligible spends (for example, NFTs, DIDs, singletons, vaults or an offer's settlement coin spent in the same spend bundle) are not part of any spend group. They contribute neither a key nor a coin ID, and MUST NOT create a silent payment output, except a settlement coin paying a party to an offer (see Payments through Settlement Coins). Because edges to and from such coins are ignored, a cycle that passes through one does not bind the eligible coins on either side of it; each eligible coin on such a cycle is its own single-input group, and an output it creates is derived from that coin alone. All coins of a multi-input group MUST be connected by a cycle through eligible spends only.
6. **Signed conditions.** The conditions output by every coin in the group MUST be committed to by that coin's signature, as they are when the delegated puzzle is a quoted list of conditions. Otherwise a third party could add or remove a concurrent-spend condition, change the group, and make the payment undetectable.
7. **Re-derive on change.** If the set of coins in the group changes after the outputs were derived — for example, a coin is added to raise the fee — the sender MUST derive all silent payment outputs again. Creating a change coin can itself add an intermediate coin to the transaction, so the outputs are derived from the group as it stands once the whole transaction has been laid out.

It is recommended that all coins in a spend group belong to a single entity. As with BIP-352, there is no security analysis of this protocol for collaboratively built transactions.

### Sending

Inputs:
- *sender_sks*: `list[int]` — synthetic secret keys, one per coin in the spend group (n >= 1)
- *coin_ids*: `list[bytes32]` — coin IDs of all coins in the spend group
- *recipients*: `list[(G1, G1)]` — list of (*B*<sub>scan</sub>, *B*<sub>m</sub>) pairs, where *B*<sub>m</sub> is the second key of the recipient's address (*B*<sub>spend</sub> for an unlabeled address). The same pair may appear more than once to create several outputs for one recipient.

Procedure **SendSilentPayment**:
* Fail if any *B*<sub>scan</sub> or *B*<sub>m</sub> in *recipients* is the identity element *O*.
* Group *recipients* by *B*<sub>scan</sub>. Fail if any group has more than *K*<sub>max</sub> entries.
* Let *a*<sub>sum</sub>: `int` = (*sender_sks*[0] + *sender_sks*[1] + ... + *sender_sks*[n-1]) mod *r*
* Fail if *a*<sub>sum</sub> == 0 ("aggregated sender key sum is zero — invalid for ECDH")
* Let *A*<sub>sum</sub>: `G1` = *a*<sub>sum</sub> · *G*
* Let *coin_id*<sub>L</sub>: `bytes32` = min(*coin_ids*) (lexicographic comparison as raw bytes)
* Let *input_hash*: `int` = int(tagged_hash("Chia_SP/Inputs", *coin_id*<sub>L</sub> || serialize(*A*<sub>sum</sub>))) mod *r*
* Fail if *input_hash* == 0
* For each group with scan key *B*<sub>scan</sub>:
  * Let *S*: `G1` = (*input_hash* · *a*<sub>sum</sub>) · *B*<sub>scan</sub>
  * Let *shared_secret*: `bytes32` = SHA256(serialize(*S*))
  * For *k* = 0, 1, ... for each (*B*<sub>scan</sub>, *B*<sub>m</sub>) entry in the group:
    * Let *t*<sub>k</sub>: `int` = int(tagged_hash("Chia_SP/SharedSecret", *shared_secret* || ser<sub>32</sub>(*k*))) mod *r*
    * Fail if *t*<sub>k</sub> == 0
    * Let *P*<sub>k</sub>: `G1` = *B*<sub>m</sub> + *t*<sub>k</sub> · *G*
    * Let *offset*: `int` = int(SHA256(serialize(*P*<sub>k</sub>) || `DEFAULT_HIDDEN_PUZZLE_HASH`), signed=True) mod *r*
    * Let *synthetic_pk*: `G1` = *P*<sub>k</sub> + *offset* · *G*
    * Let *puzzle_hash*: `bytes32` = tree_hash(curry(`p2_delegated_puzzle_or_hidden_puzzle`, *synthetic_pk*))
* Create one output for each derived *puzzle_hash*, with the appropriate amount, from a coin in the spend group.
* If n > 1, have each coin in the spend group output its `ASSERT_CONCURRENT_SPEND` condition as described in Inputs for Shared Secret Derivation.

The counter *k* increments across all entries that share a scan key, including entries with different labels. Reusing *t*<sub>k</sub> for two labels of the same recipient would let an observer who knows both labeled addresses recognize the recipient from the difference of the two outputs.

All derived outputs MUST be present in the final transaction. If the output for index *i* is omitted, the recipient will not find any output with a higher index, because scanning stops at the first index with no match.

Note: The *offset* step uses signed integer interpretation of the SHA-256 digest (see Synthetic Key Computation Note). When n=1, *a*<sub>sum</sub> is simply the single secret key and min(*coin_ids*) is the single coin ID.

The Extension to CATs adds to this procedure the asset each output is paid in and the wrapper of each coin of the spend group; every sender of version 0 MUST apply it (see Extension to CATs).

### Scanning (Detection)

#### Scanning a Spend Group

Given a spend group, the scanner aggregates the group's public keys and performs ECDH to check for silent payments. The scanner needs only the scan secret key and the spend public key; it never needs the spend secret key.

Inputs:
- *b*<sub>scan</sub>: `int` — recipient's scan secret key
- *B*<sub>spend</sub>: `G1` — recipient's spend public key
- *A*<sub>sum</sub>: `G1` — sum of the synthetic public keys of all coins in the group (for a single-input group, just the one key)
- *coin_ids*: `list[bytes32]` — coin IDs of all coins in the group
- *outputs*: `list[Coin]` — the output coins to check (see Output Matching Scope)
- *labels*: `map[G1 -> int]` — registered label public keys mapped to label index *m*

Procedure **ScanForSilentPayment**:
* If *A*<sub>sum</sub> == *O*: skip this group (zero-sum guard)
* Let *coin_id*<sub>L</sub>: `bytes32` = min(*coin_ids*) (lexicographic comparison as raw bytes)
* Let *input_hash*: `int` = int(tagged_hash("Chia_SP/Inputs", *coin_id*<sub>L</sub> || serialize(*A*<sub>sum</sub>))) mod *r*
* If *input_hash* == 0: skip this group
* Let *S*: `G1` = *b*<sub>scan</sub> · (*input_hash* · *A*<sub>sum</sub>)
* Let *shared_secret*: `bytes32` = SHA256(serialize(*S*))
* For *k* = 0, 1, 2, ..., *K*<sub>max</sub> - 1:
  * Let *t*<sub>k</sub>: `int` = int(tagged_hash("Chia_SP/SharedSecret", *shared_secret* || ser<sub>32</sub>(*k*))) mod *r*
  * If *t*<sub>k</sub> == 0: stop scanning this group
  * Let *P*<sub>k</sub>: `G1` = *B*<sub>spend</sub> + *t*<sub>k</sub> · *G*
  * Let *base_ph*: `bytes32` = puzzle_hash_for_pk(*P*<sub>k</sub>)
  * If one or more coins in *outputs* have puzzle hash *base_ph*:
    * Record a detection (*k*, *t*<sub>k</sub>, label=None, coin) for every such coin
    * Continue to *k*+1
  * For each (*label_pk*, *m*) in *labels*, in ascending order of *m*:
    * Let *P*<sub>k,m</sub>: `G1` = *P*<sub>k</sub> + *label_pk*
    * Let *labeled_ph*: `bytes32` = puzzle_hash_for_pk(*P*<sub>k,m</sub>)
    * If one or more coins in *outputs* have puzzle hash *labeled_ph*:
      * Record a detection (*k*, *t*<sub>k</sub>, label=*m*, coin) for every such coin
      * Continue to *k*+1
  * If no match at index *k*: stop scanning this group.

Note: puzzle_hash_for_pk(*P*) computes the synthetic public key and standard puzzle hash as described in the Sending section (i.e. offset, synthetic_pk, and puzzle_hash steps).

The decision to continue to *k*+1 MUST be based only on whether a match was found, never on whether the wallet considers the matched coin relevant. A match that wallet policy later filters out — a dust or spam filter, for example — still advances *k*; stopping early can cause later outputs from the same sender to be missed.

Several coins can share one puzzle hash (they differ in parent or amount). All of them are spendable with the same one-time key, so all of them are recorded.

At each index *k* the unlabeled candidate is tried first, then the labels in ascending order of *m*; the first candidate that matches is the only one recorded for that *k*. A sender that follows this CHIP never produces two matches at one index.

*labels* SHOULD always contain the change label *m* = 0 (see Labeling), even for a wallet that uses no other labels.

The Extension to CATs passes the block's wrapper list to this procedure and tests each candidate puzzle hash under every wrapper of the list as well as bare; every scanner of version 0 MUST apply it (see Extension to CATs).

#### Output Matching Scope

A scanner MUST check each spend group against all additions of the block that were created by a coin spend, not only against the children of the group's own coins, as in **ScanBlock** below. A payment to a party to an offer is created by a settlement coin, which is not in the party's spend group (see Payments through Settlement Coins), and a scanner working from tweak points has no parent information to narrow the check with. Checking more coins cannot produce a false detection, because a match needs a puzzle hash derived from the group's own shared secret.

The Extension to CATs tests each of these coins under every wrapper of the block's wrapper list as well as bare; every scanner of version 0 MUST apply it (see Extension to CATs).

#### Scanning a Block

The scanner processes each block by forming the block's spend groups (see Inputs for Shared Secret Derivation) and running **ScanForSilentPayment** on each.

Inputs:
- *b*<sub>scan</sub>: `int` — recipient's scan secret key
- *B*<sub>spend</sub>: `G1` — recipient's spend public key
- *removals*: `list[CoinSpend]` — all coin spends in the block
- *additions*: `list[Coin]` — all new coins in the block that were created by a coin spend (reward coins, which have no parent spend, are left out)
- *labels*: `map[G1 -> int]` — registered labels

Procedure **ScanBlock**:

* Let *eligible*: `list[(CoinSpend, G1)]` = every *removal* in *removals* for which eligible_spend(*removal*) returns a key *A*, paired with that key. Removals with any other puzzle are ignored from here on.
* Let *detected_coins*: `set[bytes32]` = {}

**Pass 1:** Single-input groups
* For each (*removal*, *A*) in *eligible*:
  * Run **ScanForSilentPayment**(*b*<sub>scan</sub>, *B*<sub>spend</sub>, *A*, [*removal*.coin_id], *additions*, *labels*)
  * Add any detected coin IDs to *detected_coins*

**Pass 2:** Multi-input groups
* Let *edges*: `set[(bytes32, bytes32)]` = {}
* For each (*removal*, *A*) in *eligible*:
  * Run the full puzzle reveal with its solution, as consensus does, to extract output conditions
  * For each condition with condition code 64 (`ASSERT_CONCURRENT_SPEND`):
    * Let *asserted_coin_id*: `bytes32` = the condition's first argument
    * If *asserted_coin_id* is the coin ID of a removal in *eligible*: add edge (*removal*.coin_id, *asserted_coin_id*) to *edges*
* Let *sccs*: `list[set[bytes32]]` = strongly connected components of the directed graph defined by *edges*
* For each *scc* in *sccs* where len(*scc*) >= 2:
  * Let *group*: `list[(CoinSpend, G1)]` = entries of *eligible* whose coin ID is in *scc*
  * Let *A*<sub>sum</sub>: `G1` = the sum of the keys of all entries in *group* (one term per coin)
  * Let *group_coin_ids*: `list[bytes32]` = coin IDs of all entries in *group*
  * Run **ScanForSilentPayment**(*b*<sub>scan</sub>, *B*<sub>spend</sub>, *A*<sub>sum</sub>, *group_coin_ids*, *additions*, *labels*)
  * Add any detected coin IDs not already in *detected_coins*

Every coin of a multi-input group is also scanned on its own in Pass 1. This costs one extra ECDH per coin and keeps the scanner independent of how a sender chose to bind its coins.

The Extension to CATs widens the set of eligible spends and the outputs a scanner must test, and adds the block's wrapper list; every scanner of version 0 MUST apply it (see Extension to CATs).

#### Tweak Points

Everything a scanner needs from a spend group's inputs is contained in a single G1 point, the group's *tweak point*:

* *T* = *input_hash* · *A*<sub>sum</sub>

The scanner's shared secret is then SHA256(serialize(*b*<sub>scan</sub> · *T*)), and the rest of **ScanForSilentPayment** is unchanged. The tweak points of a block are one *T* for each spend group of the block — every single-input group and every multi-input group — leaving out groups where *A*<sub>sum</sub> == *O* or *input_hash* == 0.

Tweak points let the party that forms the spend groups differ from the party that holds the scan key (see Appendix A). A scanner that receives tweak points from another party, instead of computing them itself:

- MUST verify that each *T* is a valid element of the prime-order G1 subgroup and is not the identity element before multiplying it by *b*<sub>scan</sub>, and MUST skip any tweak point that fails this check;
- checks each *T* against all additions of the block that were created by a coin spend (see Output Matching Scope).

The Extension to CATs adds the block's wrapper list, which tweak points do not carry, to what such a scanner needs; every scanner of version 0 MUST apply it (see Extension to CATs).

### Spending

The Extension to CATs describes how an output in a CAT is spent (see Extension to CATs).

#### Unlabeled Output

Inputs:
- *b*<sub>spend</sub>: `int` — recipient's spend secret key
- *t*<sub>k</sub>: `int` — recorded tweak from scanning at output index *k*

Procedure **SpendUnlabeled**:
* Let *b*<sub>onetime</sub>: `int` = (*b*<sub>spend</sub> + *t*<sub>k</sub>) mod *r*
* Let *P*<sub>onetime</sub>: `G1` = *b*<sub>onetime</sub> · *G*
* Let *offset*: `int` = int(SHA256(serialize(*P*<sub>onetime</sub>) || `DEFAULT_HIDDEN_PUZZLE_HASH`), signed=True) mod *r*
* Let *b*<sub>synthetic</sub>: `int` = (*b*<sub>onetime</sub> + *offset*) mod *r*
* Sign the delegated puzzle hash, coin ID, and `AGG_SIG_ME` additional data using *b*<sub>synthetic</sub>.

#### Labeled Output

Inputs:
- *b*<sub>spend</sub>: `int` — recipient's spend secret key
- *b*<sub>scan</sub>: `int` — recipient's scan secret key (for label scalar derivation)
- *t*<sub>k</sub>: `int` — recorded tweak from scanning at output index *k*
- *m*: `int` — detected label index

Procedure **SpendLabeled**:
* Let *label_scalar*: `int` = int(tagged_hash("Chia_SP/Label", ser<sub>256</sub>(*b*<sub>scan</sub>) || ser<sub>32</sub>(*m*))) mod *r*
* Let *b*<sub>onetime</sub>: `int` = (*b*<sub>spend</sub> + *t*<sub>k</sub> + *label_scalar*) mod *r*
* Let *P*<sub>onetime</sub>: `G1` = *b*<sub>onetime</sub> · *G*
* Let *offset*: `int` = int(SHA256(serialize(*P*<sub>onetime</sub>) || `DEFAULT_HIDDEN_PUZZLE_HASH`), signed=True) mod *r*
* Let *b*<sub>synthetic</sub>: `int` = (*b*<sub>onetime</sub> + *offset*) mod *r*
* Sign the delegated puzzle hash, coin ID, and `AGG_SIG_ME` additional data using *b*<sub>synthetic</sub>.

A scanner that holds only *b*<sub>scan</sub> can hand the signer the single value (*t*<sub>k</sub> + *label_scalar*) mod *r* for each detected coin. The signer then needs only *b*<sub>spend</sub>, and the two procedures above collapse into one.

### Labeling

Labels allow a recipient to generate multiple distinct silent payment sub-addresses from a single key pair, enabling the recipient to distinguish payment streams (e.g., "donations" vs. "invoices") while maintaining unlinkability from an observer's perspective.

#### Label Generation

For label index *m* (where *m* = 0 is reserved for change outputs):

* Let *label_scalar*: `int` = int(tagged_hash("Chia_SP/Label", ser<sub>256</sub>(*b*<sub>scan</sub>) || ser<sub>32</sub>(*m*))) mod *r*
  where ser<sub>256</sub>(*b*<sub>scan</sub>) is the 32-byte big-endian representation of the scan secret key scalar.
* Let *label_pk*: `G1` = *label_scalar* · *G*
* Let *B*<sub>m</sub>: `G1` = *B*<sub>spend</sub> + *label_pk*

The labeled silent payment address is (*B*<sub>scan</sub>, *B*<sub>m</sub>). Note that *B*<sub>scan</sub> is unchanged — the scan key is shared across all labels.

#### Change Detection (m = 0)

Label *m* = 0 is reserved for change outputs. When the sender is also the recipient, sending change back to themselves, they construct the change output using (*B*<sub>scan</sub>, *B*<sub>0</sub>) where *B*<sub>0</sub> = *B*<sub>spend</sub> + *label_pk*<sub>0</sub>. A wallet MUST NOT hand out the address with label *m* = 0 to anyone else, so that nobody else can create payments that are wrongly identified as change.

#### Label Linkability Note

Two labeled addresses from the same recipient share the same *B*<sub>scan</sub>. An observer comparing two labeled addresses can determine they belong to the same recipient by comparing the scan key component. Recipients who require unlinkability between payment streams should use separate wallets with independent key pairs.

#### Scanning Cost of Labels

Because outputs are puzzle hashes, a scanner cannot recover a label from an output; it has to derive a candidate puzzle hash for every registered label. For each spend group that does not pay the scanner — which is almost all of them — the scanner computes one ECDH, one *t*<sub>0</sub> · *G*, and then one puzzle hash for the unlabeled case plus one for each label. Each puzzle hash costs a point addition, a G1 scalar multiplication (the synthetic offset), and a tree hash. Scanning cost therefore grows linearly with the number of labels, for every spend group on the chain.

This differs from BIP-352, where the cost of labels is independent of how many are registered, and it means BIP-352's advice to scan for a very large number of labels during recovery does not carry over. Wallets SHOULD keep the number of labels small, SHOULD allocate label indices sequentially starting from 1, and SHOULD record the highest index handed out.

### Backup and Recovery

Each silent payment output is derived independently, so a wallet cannot find its coins by querying for known puzzle hashes. Recovering from a mnemonic means scanning again: every transaction block from the wallet's birthday onward has to be processed as in Scanning a Block (or its tweak points obtained from another party). Wallets SHOULD record the height at which the silent payment address was first published and include it in backups, so that recovery does not have to start from the first block.

If a wallet uses labels, the highest label index handed out SHOULD be included in the backup. When it is not known, the recovering wallet has to choose a range of labels to scan for and accept the cost described above. The change label *m* = 0 SHOULD always be scanned for, even when no other labels were used, so that the use of the change label is never critical for recovery and wallets remain compatible with one another.

### Tagged Hash

This protocol uses BIP-340-style tagged hashing for domain separation. The tagged hash function is:

* tagged_hash(*tag*, *data*) = SHA256(SHA256(*tag*) || SHA256(*tag*) || *data*)

where *tag* is a UTF-8 encoded string and *data* is arbitrary bytes.  The following domain tags are used:
- `"Chia_SP/Inputs"` — Input hash computation
- `"Chia_SP/SharedSecret"` — Output tweak derivation
- `"Chia_SP/Label"` — Label scalar generation

The `"Chia_SP/"` prefix provides domain separation from other protocols using tagged hashes (e.g., Bitcoin's `"BIP0352/"` tags).

### Recognizing an Eligible Spend

The procedure **eligible_spend** below is the only recognizer of eligible spends; Definitions, Scanning a Block and Security refer to it.

The standard puzzle `p2_delegated_puzzle_or_hidden_puzzle`, when curried with a synthetic public key, has the structure:

(a (q . MOD) (c (q . SYNTHETIC_PK) 1))

The synthetic public key is the first curried argument. A puzzle *is the standard puzzle* when it uncurries to the `p2_delegated_puzzle_or_hidden_puzzle` module curried with exactly this one argument.

Inputs:
- *spend*: `CoinSpend` — a coin spend, with its puzzle reveal and solution

Procedure **eligible_spend**, returning *A*: `G1`, or none:
* If *spend*.puzzle_reveal is the standard puzzle: return its synthetic public key
* Return none

Implementations MUST verify that the puzzle's uncurried module matches the known `p2_delegated_puzzle_or_hidden_puzzle` tree hash (`e9aaa49f45bad5c889b86ee3341550c155cfdd10c3a6757de618d20612fffd52`) before accepting the extracted key.

The Extension to CATs adds two kinds of eligible spend to this procedure, the standard puzzle inside `cat_v2` and inside `cat_v2` and the revocation layer on the holder's path, and has it return the spend's wrapper as well; every implementation of version 0 MUST use the procedure as extended there (see Extension to CATs).

### Synthetic Key Computation Note

The synthetic offset computation uses signed integer interpretation of the SHA-256 digest, following the Chia standard:

*offset* = int.from_bytes(SHA256(*pk* || *hidden_puzzle_hash*), "big", signed=True) mod *r*

This matches the behavior of Chia's `int_from_bytes` function. Implementations MUST use signed interpretation to produce correct puzzle hashes.

### *K*<sub>max</sub>: Maximum Outputs Per Spend Group

The scanner iterates output indices *k* = 0, 1, 2, ... for each spend group until no match is found. *K*<sub>max</sub> is a limit shared by both sides, so that no valid payment lies beyond the point where a scanner stops:

- A sender MUST NOT create more than *K*<sub>max</sub> outputs for a single scan key *B*<sub>scan</sub> in one spend group.
- A scanner MUST be able to detect outputs at every index below *K*<sub>max</sub>, and MUST stop iterating for a spend group when *k* reaches *K*<sub>max</sub>, so that all scanners find the same set of payments.

The Extension to CATs counts the outputs of every asset toward this bound (see Extension to CATs).

#### Derivation from Chia Block Constraints

Chia cost constants:

| Constant | Value | Source |
|----------|-------|--------|
| Maximum block cost | 11,000,000,000 | Chia consensus |
| Maximum spend bundle cost | 5,500,000,000 | Mempool rule (half of block cost) |
| CREATE_COIN cost | 1,800,000 | CLVM condition cost |
| AGG_SIG_ME cost | 1,200,000 | CLVM condition cost |
| Byte cost | 12,000 | CLVM byte multiplier |

Per-output minimum cost:
- CREATE_COIN condition: 1,800,000
- Output puzzle hash (32 bytes): 32 · 12,000 = 384,000
- Output amount (up to 8 bytes): 8 · 12,000 = 96,000
- **Per-output total: ~2,280,000**

Single-spend baseline overhead (from reference implementation tests):
- CLVM execution: ~27,000
- AGG_SIG_ME: 1,200,000
- Byte cost (~433 bytes for puzzle reveal + solution): ~5,196,000
- **Baseline total: ~6,423,000**

Maximum outputs from a single spend bundle:
- Available cost: 5,500,000,000 - 6,423,000 = 5,493,577,000
- Theoretical maximum: floor(5,493,577,000 / 2,280,000) = 2,409

***K*<sub>max</sub> = 2,400** (at the theoretical maximum for a single spend bundle).

BIP-352 uses *K*<sub>max</sub> = 2,323 (derived from Bitcoin's 100 kvB standardness limit). The Chia value is comparable.

Note: The spend bundle cost limit (5.5B) is a mempool policy, not a consensus rule. A farmer could theoretically include a spend bundle using the full block cost (11B), which would allow ~4,800 outputs. *K*<sub>max</sub> = 2,400 covers the standard mempool case.

Candidate puzzle hashes are matched by lookup, so a scanner's work for a spend group is proportional to the number of outputs that actually pay it (times the number of labels it scans for), not to the number of outputs in the block. *K*<sub>max</sub> bounds the work that a single transaction paying the scanner can cause.

### Edge Cases

#### Identity Element (Zero-Sum Prevention)

When aggregating sender keys for multi-input sends, the sum may equal zero (e.g., the aggregated public key is the identity element *O*). This occurs if the individual secret keys happen to cancel out modulo *r*.

- **Sender side:** If *a*<sub>sum</sub> == 0, the sender MUST abort the transaction with an error. ECDH with the identity element produces a predictable shared secret (SHA256 of the serialized identity point), which would be the same for all recipients and all transactions. This is a catastrophic privacy failure.
- **Scanner side:** If *A*<sub>sum</sub> == *O* (identity element after point addition), the scanner MUST skip this spend group. The identity element check is: serialize(*A*<sub>sum</sub>) == serialize(*O*), or equivalently, *A*<sub>sum</sub> is the point at infinity.

The probability of a random zero-sum is approximately 1/*r*, negligible for BLS12-381's 255-bit group order. However, a malicious sender could construct a zero-sum deliberately, so the check is a defense-in-depth measure.

#### Zero Scalars

The values *input_hash* and *t*<sub>k</sub> are hashes reduced mod *r*, and each is zero with probability about 1/*r*. A zero *input_hash* would make the shared secret independent of the sender's keys, and a zero *t*<sub>k</sub> would make the one-time key equal to the address's own spend key. Senders fail in either case; scanners skip the group or stop iterating, as given in the procedures above.

A *label_scalar* of zero would make the labeled address identical to the unlabeled one. A wallet MUST NOT use a label index whose *label_scalar* is zero.

#### Outputs Sharing a Puzzle Hash

Two or more output coins can carry the same one-time puzzle hash, for example when two coins of a spend group each create a coin for it, or when one coin creates two such coins with different amounts. They are all spendable with the same one-time key, and a scanner records every one of them.

### Extension to CATs

The sections above define the protocol for XCH. This section extends it to CATs held in the standard puzzle, including revocable CATs ([CHIP-0038](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0038.md)): CAT coins become eligible spends, one spend group can hold XCH and CAT coins, and a silent payment output can be a CAT coin. The extension is part of version 0, not an option: every sender and scanner of version 0 MUST follow it. Each section above whose rules it changes says so in one sentence.

With no CAT coin spent in a transaction, the extension changes nothing: a transaction whose eligible spends are all XCH has the spend groups, tweak points and detections of the sections above. A scanner that implements the sections above without the extension finds no payment from a spend group holding both XCH and CAT coins and no payment in a CAT.

#### Wrappers

- **Wrapper**: The layers around the standard puzzle of a CAT coin, written as the pair *W* = (*asset_id*, *hidden_ph*) of type `Wrapper`: *asset_id* is the 32-byte asset ID of the CAT (the hash of its TAIL) in the [`cat_v2`](https://docs.chia.net/cats/) layer, and *hidden_ph* is, for a revocable CAT, the 32-byte hidden puzzle hash of the CHIP-0038 revocation layer, or none otherwise. An XCH coin held in the standard puzzle has no wrapper (*W* = none). Two wrappers are equal when both fields are equal as bytes, and none equals only none.
- **wrap(*W*, *h*)**: The puzzle hash of a coin with wrapper *W* whose inner standard puzzle has tree hash *h*. wrap(none, *h*) = *h*. Otherwise, let *h'* = *h* if *hidden_ph* is none, and else the tree hash of the revocation layer curried with (`REVOCATION_MOD_HASH`, *hidden_ph*, *h*), all three curried as 32-byte atoms, because the revocation layer holds the holder's puzzle as a hash; wrap(*W*, *h*) is then the tree hash of `cat_v2` curried with (`CAT_MOD_HASH`, *asset_id*, inner puzzle), where the first two are 32-byte atoms and the inner puzzle is a full puzzle, not an atom, with tree hash *h'*. Both tree hashes are computed from tree hashes alone, without the inner puzzle itself. The module hashes are listed in Eligible CAT Spends.

#### Eligible CAT Spends

This extension widens the closed list of eligible spends. With it, an eligible spend is a coin spend for which eligible_spend returns a key: a spend whose puzzle is the standard puzzle, either bare, inside `cat_v2`, or inside `cat_v2` and the revocation layer of [CHIP-0038](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0038.md) spent on the holder's path. Its key is the synthetic public key of that standard puzzle, and its coin ID is the spent coin's own. No other spend is eligible in version 0.

The extended procedure recognizes two more modules by their tree hashes:
- `cat_v2` (`CAT_MOD_HASH`): `37bef360ee858133b69d595a906dc45d01af50379dad515eb9518abb7c1d2a7a`
- the revocation layer of [CHIP-0038](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0038.md) (`REVOCATION_MOD_HASH`): `00848115554ea674131f89f311707a959ad3f4647482648f3fe91ba289131f51`

With the extension, **eligible_spend** returns the pair (*A*, *W*) of the spend's key and its wrapper, or none, and replaces the procedure of Recognizing an Eligible Spend; where the core protocol uses the returned key, it uses *A*.

Inputs:
- *spend*: `CoinSpend` — a coin spend, with its puzzle reveal and solution

Procedure **eligible_spend**, returning (*A*: `G1`, *W*: `Wrapper` or none), or none:
* If *spend*.puzzle_reveal is the standard puzzle: return (its synthetic public key, none)
* Unless *spend*.puzzle_reveal is exactly `cat_v2` — its uncurried module has tree hash `CAT_MOD_HASH`; it has exactly three curried arguments, the first equal to `CAT_MOD_HASH`, the second a 32-byte atom *asset_id*, and the third a puzzle *inner*; and its tree hash equals wrap((*asset_id*, none), tree_hash(*inner*)) — return none
* If *inner* is the standard puzzle: return (its synthetic public key, (*asset_id*, none))
* Unless *inner* is exactly the revocation layer — its uncurried module has tree hash `REVOCATION_MOD_HASH`; it has exactly three curried arguments, each a 32-byte atom, the first equal to `REVOCATION_MOD_HASH`; and its tree hash equals the tree hash of the revocation layer curried with those three atoms — return none
* Let *hidden_ph*: `bytes32` and *inner_ph*: `bytes32` be the second and third curried arguments of *inner*
* Let *hidden_flag* and *revealed* be the first two elements of the CAT layer's inner solution, which is the first element of *spend*.solution; if the solution does not have this shape, return none
* If *hidden_flag* is not nil: return none (the issuer's hidden path is not the holder's spend)
* If tree_hash(*revealed*) != *inner_ph*: return none
* If *revealed* is the standard puzzle: return (its synthetic public key, (*asset_id*, *hidden_ph*))
* Return none

As for the standard puzzle (see Recognizing an Eligible Spend), implementations MUST require the exact module hash, the exact curried arguments and the matching tree hash of the whole layer for `cat_v2` and for the revocation layer, as in the procedure above: a puzzle that only looks like one of these layers must not contribute a key to a spend group.

For a revocable CAT, the key is read from the holder puzzle revealed in the solution, because the revocation layer holds only the hash of that puzzle.

A spend that matches none of the three shapes is not eligible, for example a CAT inside a CAT, a CAT around an offer's settlement coin, or a revocable CAT spent through the issuer's hidden path.

#### Wrapper List of a Block

The **wrapper list of a block** is the list of the distinct wrappers of every CAT coin spent in the block, whatever its innermost puzzle. Every coin spend whose puzzle reveal is exactly `cat_v2`, as matched in eligible_spend, adds its wrapper, so a settlement coin of an offer, a revocable CAT spent through the issuer's hidden path and any other CAT spend that is not eligible all count. The wrapper of such a spend is (*asset_id*, *hidden_ph*) when its `cat_v2` inner puzzle is exactly the revocation layer, as matched in eligible_spend, and (*asset_id*, none) otherwise. The list is given in a fixed, total order: by *asset_id* as bytes, and for one asset ID the wrapper without a hidden puzzle hash first, then by *hidden_ph* as bytes. The order affects no detection, since a scanner tests every wrapper of the list; it exists so that every server sends the same list for a block. A CAT coin created by a coin that is not a CAT (a mint) can carry a wrapper that is not in the list; such a coin is not a silent payment output in version 0.

#### Spend Groups across Assets

The concurrent-spend graph of Inputs for Shared Secret Derivation takes the block's eligible spends as vertices whatever their asset: an XCH coin, a CAT coin and a revocable CAT coin are vertices of one graph. The conditions of a CAT spend, output by running its full puzzle reveal with its solution as consensus does, include what the CAT layer (and, for a revocable CAT, the revocation layer) outputs. One cycle over XCH and CAT coins is therefore one spend group, with one key sum *A*<sub>sum</sub>, one tweak point and one output counter *k* across assets.

A coin that is not an eligible spend adds no vertex and no edge, as in the core protocol, even when it lies on a cycle between eligible coins; a settlement coin, a CAT inside a CAT and a revocable CAT spent through the issuer's hidden path are examples. Sender requirement 2 counts every eligible spend in the cycle, whatever its asset, with one term per coin.

#### Outputs in CATs

A silent payment output in a CAT is a coin of the standard puzzle with a one-time key under the wrapper of its asset. Sender requirement 4 holds per asset: every silent payment output MUST be created by — that is, have as its parent — a coin of the output's asset in the spend group, or by a settlement coin whose puzzle announcement of that payment a coin of the group asserts (see Payments through Settlement Coins).

The counter *k* increments across all entries that share a scan key, including entries with different labels or assets. The *K*<sub>max</sub> bound counts the outputs to that scan key in every asset, including outputs paid through a settlement coin; its value is unchanged by the support for CATs.

The sender builds the transaction exactly as a wallet does. The standard puzzle of a CAT coin names the bare one-time puzzle hash in its CREATE_COIN condition, and the CAT layer, with the revocation layer for a revocable CAT (which wraps created coins itself), produces the coin with puzzle hash wrap(*W*, *puzzle_hash*). A CAT output carries the 32-byte bare one-time puzzle hash as its hint memo, as a wallet hints any CAT payment with the recipient's inner puzzle hash; an XCH output carries no memo.

As in Outputs Sharing a Puzzle Hash, the same holds across assets: coins of different assets created for one one-time puzzle hash each have puzzle hash wrap(*W*, one-time puzzle hash) for their own wrapper *W*, and all of them are recorded.

A CAT output is spent with the same one-time key as an XCH output, through its CAT layer and, for a revocable CAT, the revocation layer's holder path, in the way any CAT coin held in the standard puzzle is spent.

#### Matching Outputs under Wrappers

A scanner MUST test every coin of the block that was created by a coin spend (see Output Matching Scope) bare and under every wrapper of the block's wrapper list, as **ScanForSilentPayment** does with the changes below. A candidate is tested bare and under every wrapper of the list at once: every coin it matches under any wrapper is recorded, and no later candidate is tried at that index. With an empty wrapper list (no CAT coin spent in the block) every candidate is tested bare only.

#### Changes to the Procedures

The procedures of the core protocol change as follows; every step not named here is unchanged.

**SendSilentPayment** (see Sending):
- Two more inputs:
  - *coin_wrappers*: `list[Wrapper or none]` — the wrapper of each coin in the spend group, in the order of *coin_ids* (none for an XCH coin)
  - *amounts*: `list[int]` — the amount paid to each entry, in the order of *recipients*
- *recipients* becomes `list[(G1, G1, Wrapper or none)]`, a list of (*B*<sub>scan</sub>, *B*<sub>m</sub>, *W*) entries, where *W* is the asset the entry is paid in (none for XCH).
- After the first Fail step, one more step:
  * Fail if the *W* of any entry is not in *coin_wrappers* (an output must be created by a coin of the same asset in the spend group).
- The grouping step becomes:
  * Group *recipients* by *B*<sub>scan</sub>, keeping their order; entries of different assets share a group. Fail if any group has more than *K*<sub>max</sub> entries.
- The loop over *k* runs over the (*B*<sub>scan</sub>, *B*<sub>m</sub>, *W*) entries of the group; its steps do not use *W*.
- The step that creates the outputs becomes:
  * For each entry and its derived *puzzle_hash*, have a coin of the spend group whose wrapper is the entry's *W* output CREATE_COIN(*puzzle_hash*, *amount*), where *amount* is the entry's amount in *amounts*, with the memo list (*puzzle_hash*) when *W* is not none. The coin's layers wrap the created puzzle hash, so the coin created has puzzle hash wrap(*W*, *puzzle_hash*).

**ScanForSilentPayment** (see Scanning a Spend Group):
- One more input:
  - *wrappers*: `list[Wrapper]` — the wrapper list of the block (see Wrapper List of a Block)
- The unlabeled match step becomes:
  * If one or more coins in *outputs* have a puzzle hash among the candidates wrap(*W*, *base_ph*) for *W* in [none] followed by *wrappers*:
    * Record a detection (*k*, *t*<sub>k</sub>, label=None, *W*, coin) for every such coin, *W* being the wrapper under which it matched
    * Continue to *k*+1
- The labeled match step becomes:
  * If one or more coins in *outputs* have a puzzle hash among the candidates wrap(*W*, *labeled_ph*) for *W* in [none] followed by *wrappers*:
    * Record a detection (*k*, *t*<sub>k</sub>, label=*m*, *W*, coin) for every such coin, *W* being the wrapper under which it matched
    * Continue to *k*+1

**ScanBlock** (see Scanning a Block):
- *eligible* pairs each removal with the key *A* of eligible_spend as extended above, so the spend groups form over the eligible spends of every asset.
- After the step that computes *eligible*, one more step:
  * Let *wrappers*: `list[Wrapper]` = the wrapper list of the block, computed from *removals* (see Wrapper List of a Block)
- Both passes pass *wrappers* after *additions*:
  * Run **ScanForSilentPayment**(*b*<sub>scan</sub>, *B*<sub>spend</sub>, *A*, [*removal*.coin_id], *additions*, *wrappers*, *labels*)
  * Run **ScanForSilentPayment**(*b*<sub>scan</sub>, *B*<sub>spend</sub>, *A*<sub>sum</sub>, *group_coin_ids*, *additions*, *wrappers*, *labels*)
- In Pass 2, running the full puzzle reveal of a CAT spend gives the conditions the CAT layer (and, for a revocable CAT, the revocation layer) outputs (see Spend Groups across Assets).

**Tweak points** (see Tweak Points): a scanner working from tweak points also needs the block's wrapper list, which tweak points do not carry, and tests each candidate puzzle hash bare and under each wrapper of the list. The same holds when tweak points are obtained from another party for recovery (see Backup and Recovery) or by a light client (see Appendix A: Light Client Support).

#### Rationale for the Extension

- **One group across assets:** Wallets already bind the XCH and CAT coins of one transaction with `ASSERT_CONCURRENT_SPEND`. In a survey of recent mainnet blocks, 53 concurrent-spend cycles held both XCH and CAT coins in the standard puzzle, against 17 that held XCH coins only; in a range one year earlier the counts were 110 and 35. Treating CAT coins as eligible spends lets a silent payment come from the transaction a wallet builds anyway, with one key sum and one output counter.
- **Coins that are not eligible do not bind:** Letting a coin that is not eligible bind a cycle without contributing a key was measured on three mainnet ranges, where the two rules differ by one group in total, and rejected: it would change almost nothing, and it adds the attack described in Rationale.

### Payments through Settlement Coins

In an offer, a party's requested payment is created by a settlement coin, not by a coin of the party. This section lets a party to an offer be paid at a silent payment address, usually its own. The settlement puzzle, the offer file format and the nonce of a requested payment are defined by the [offers documentation](https://docs.chia.net/offers/) and are not restated here.

A **settlement coin** is a coin of the offers settlement puzzle `settlement_payments` (tree hash `cfbfdeed5c4ca2de3d0bf520b9cb4bb7743a359bd2e6a188d19ce7dffc21d3e7`, named `SETTLEMENT_PAYMENTS_HASH` here), bare for XCH or under a CAT wrapper, through which an offer pays a party; the offers documentation defines it. A settlement coin is never an eligible spend. When it is a CAT coin, its wrapper is in the block's wrapper list.

**The rule.** A party to an offer derives the one-time puzzle hash of a requested payment from its own spend group — the eligible coins it spends in the offer, grouped as in Inputs for Shared Secret Derivation — and a silent payment address, exactly as in Sending. The settlement coin of the payment's asset *W* creates the coin wrap(*W*, one-time puzzle hash). A coin of the party's spend group MUST assert the settlement coin's puzzle announcement of the notarized payment that lists the payment (`ASSERT_PUZZLE_ANNOUNCEMENT`, condition code 63): one announcement for each asset of the party's requested payments, over all of its requested payments in that asset, as **DeriveSettlementOutputs** computes it. The assertion is what ties the payment to the party's transaction: the party's spends are valid only in a block in which the settlement coin makes that payment. A counterparty cannot do the derivation for the party, because the party's signature fixes its requested payment before any counterparty exists.

Inputs:
- *sender_sks*: `list[int]`, *coin_ids*: `list[bytes32]`, *coin_wrappers*: `list[Wrapper or none]` — the party's spend group, as in **SendSilentPayment** with the Extension to CATs (see Changes to the Procedures)
- *recipients*: `list[(G1, G1, Wrapper or none, bool)]` — the party's recipient entries as in **SendSilentPayment**, each with a flag *settled* that is true when the entry is paid through the settlement coin of its asset *W*. The entries include the party's own outputs, such as its change, as well as its requested payments to silent payment addresses.
- *amounts*: `list[int]` — the amount paid to each entry, in the order of *recipients*
- *other_payments*: `list[(Wrapper or none, payment)]` — the party's requested payments to addresses that are not silent payment addresses, each with its asset *W* and the payment as the party lists it in its offer; usually empty
- *nonce*: `bytes32` — the offer's nonce for the party's requested payments, as defined by the offers documentation

Procedure **DeriveSettlementOutputs**:
* Run the derivation steps of **SendSilentPayment** once over the (*B*<sub>scan</sub>, *B*<sub>m</sub>, *W*) of every entry of *recipients*, with *amounts*, giving one *puzzle_hash* per entry, with one *k* sequence per scan key that covers the entries paid through a settlement coin and the party's own outputs alike. The Fail step for an asset that no coin of the group holds does not apply to an entry whose *settled* flag is true.
* Let *settlement_outputs* and *assertions* be empty lists
* For each entry whose *settled* flag is true, with derived *puzzle_hash* *p*, amount *amount* and wrapper *W*:
  * Let *payment* = (*p*, *amount*, ()) if *W* is none, else (*p*, *amount*, (*p*)): the third element is the memo list, empty for XCH and holding the hint of a CAT payment
  * Append wrap(*W*, *p*), the puzzle hash of the coin that the settlement coin of asset *W* must create, to *settlement_outputs*
* For each asset *W* of the party's requested payments:
  * Let *payments* = the party's requested payments in asset *W*, in the order the party lists them in its offer: the *payment* of each settled entry paid in *W*, and each payment of *other_payments* in *W*
  * Let *notarized* = (*nonce* . *payments*)
  * Let *announcement*: `bytes32` = SHA256(wrap(*W*, `SETTLEMENT_PAYMENTS_HASH`) || tree_hash(*notarized*))
  * Append the condition `ASSERT_PUZZLE_ANNOUNCEMENT`(*announcement*) to *assertions*
* Let *group_outputs* be the outputs of every entry whose *settled* flag is false, each created by a coin of the spend group as in the output step of **SendSilentPayment**
* Return (*settlement_outputs*, *assertions*, *group_outputs*)

A coin of the spend group MUST output each condition of *assertions*; like every condition of a coin in the group, it is committed to by that coin's signature (sender requirement 6). The party's offer lists each settled entry's *payment* exactly as above, in the notarized payment of its asset, so that each announcement the party asserts is one the settlement coin creates.

Here (...) is a CLVM list, () the empty list, (*x* . *y*) a CLVM pair, *amount* a CLVM integer, and tree_hash the CLVM tree hash, as the offers documentation uses them for a notarized payment. An XCH payment carries the empty memo list as its third element: the Chia reference wallet rebuilds every requested payment with a memo list when it takes an offer, and (*p*, *amount*) and (*p*, *amount*, ()) have different tree hashes.

The derivation runs once over all of the party's entries because its outputs to one scan key share one counter. Two separate *k* sequences would use *t*<sub>0</sub> for two outputs of one scan key, which Sending explains is linkable, and a scanner would find only one of them. The counter *k*, *K*<sub>max</sub> and sender requirement 7 (re-derive on change) apply to the party's whole spend group. The hint applies only to a CAT payment (see Outputs in CATs). The settlement coin is never an eligible spend, but as a CAT coin it adds its wrapper to the block's wrapper list (see Wrapper List of a Block).

**Maker paid silently.** The maker offers XCH from two coins bound in a cycle and requests a CAT. It derives the CAT payment at *k* = 0 from its spend group and its own address, and its XCH change at *k* = 1 with label 0, created by one of its own coins. A coin of the maker asserts the CAT settlement coin's puzzle announcement of the payment, and the CAT settlement coin funded by the taker creates wrap(*W*, *p*).

**Taker paid silently.** The taker gives a CAT from one coin and is paid XCH at *k* = 0 through the XCH settlement coin. Its CAT change is at *k* = 1 with label 0.

**Both parties.** When both parties are paid silently, each derives from its own spend group independently, and neither needs the other's keys.

**Scanning.** Nothing offer-specific is required of the scanner. The payment is created by a settlement coin, which every scanner already checks, because Output Matching Scope covers every coin created in the block; and a CAT settlement coin is spent in the same block, so its wrapper is in the block's wrapper list. The party's spend group is formed from its own coins, and the settlement coin adds no vertex to the concurrent-spend graph.

**A party with no eligible coin.** A party that spends no eligible coin in the offer has no spend group, and cannot be paid at a silent payment address through an offer in version 0.

The rule covers a settlement coin of any asset *W*, including a revocable CAT.

The values are generated by the reference implementation and reproduced by the implementations listed under Reference Implementation.

Vectors 9 through 11 exercise the Extension to CATs and Vectors 12 and 13 Payments through Settlement Coins, with the given recipient keys of Vectors 1 through 7. The sender's keys are derived from the BIP-39 test mnemonic (`abandon` × 11, `about`) at Chia's standard wallet path, `m/12381/8444/2/<index>`.

### Format of the Vector File

Integers are 32-byte big-endian hex, points are 48-byte compressed G1 elements, and a wrapper is an object with `asset_id` and `hidden_puzzle_hash` (null for a CAT without a revocation layer). The file has these top-level members:

- `payments` — Vectors 1 through 4, 6, 7 and 9 through 11. Each has `inputs` (per coin: `coin_id`, `synthetic_sk`, `synthetic_pk` and, for a CAT coin, `wrapper`), `a_sum_pk`, `coin_id_l`, `input_hash`, `tweak_point` and `outputs`. Each output has `k`, `recipient` (the scan and spend keys and the label), `shared_secret`, `t_k`, `onetime_pk`, `onetime_sk`, `spend_tweak` = (*t*<sub>k</sub> + *label_scalar*) mod *r*, and `puzzle_hash`; an output in a CAT adds `wrapper`, `wrapped_puzzle_hash`, `hint` and `amount`.
- `settlement_payments` — Vectors 12 and 13. Each adds `party`, `nonce`, `other_payments`, `notarized_payments` (per asset, with the settlement coin's puzzle hash and the payments as listed in the offer), `settlement_outputs`, `assertions`, `group_outputs` and `wrapper_list`, and marks each output `settled` or not; `negative_controls` gives the detections without the wrapper list and the announcement of an XCH payment listed without its memo list.
- `labels` — the label scalar and label key for m = 0 and m = 1 under the scan key of Vector 1.
- `addresses` and `address_cases` — Vector 5: the four addresses, and sixteen encoding cases, each marked valid or invalid.
- `key_derivation` — Vector 8: the mnemonic, the master key, the scan and spend paths, keys and addresses.

### Required Behaviors

Implementations should also test the following cases, which have no intermediate values to list:

**Addresses**
- A version 31 address is rejected.
- A version 0 address whose payload is not exactly 96 bytes is rejected.
- A version 1 through 30 address with extra payload bytes is accepted, using the first 96 bytes.
- An address in which either key is the identity element, is not on the curve, or is outside the prime-order subgroup is rejected.
- An address with non-zero padding bits, mixed case, a wrong checksum, or more than 1,023 characters is rejected; an all-upper-case address is accepted.

**Sending**
- A spend group whose secret keys sum to zero mod *r* makes the sender fail.
- More than *K*<sub>max</sub> outputs for one scan key in one spend group makes the sender fail.
- When the sender's cycle includes an intermediate coin created inside the transaction, that coin's key and coin ID are included in *a*<sub>sum</sub> and *coin_id*<sub>L</sub>, and the recipient detects the payment.

**Scanning**
- A spend group whose public keys sum to the identity element is skipped.
- A spend that asserts a group member's coin ID without being asserted back is not part of that group, and the payment is still detected.
- A spend that is not an eligible spend contributes no key, no coin ID, and no edge, even when it outputs `ASSERT_CONCURRENT_SPEND` conditions.
- Two output coins with the same one-time puzzle hash are both reported.
- A matching output that wallet policy filters out still advances *k*.

The following cases test Extension to CATs and Payments through Settlement Coins:

**Sending with CATs**
- An XCH coin and a CAT coin bound in one cycle form one spend group, and outputs in both assets to one scan key share one sequence of *k*.
- A CAT coin spent alone is a single-input spend group, and its CAT output is found.
- An output in an asset that no coin of the spend group holds makes the sender fail.
- A revocable CAT spent on the holder's path is an eligible spend, its key read from the holder puzzle revealed in the solution, and its output keeps the revocation layer.

**Scanning with CATs**
- A spend through the revocation layer's hidden (issuer) path is not an eligible spend, nor is a revocable CAT whose revealed holder puzzle does not match the hash the layer holds, nor a CAT inside a CAT.
- A wallet's cycle that passes through a coin that is not an eligible spend binds nothing: each eligible coin is its own spend group, a payment derived from the one coin that creates it is found, and the same payment derived from both eligible coins together is not.
- A CAT coin spent in the block whose inner puzzle is not the standard puzzle (a settlement coin, for example) is not an eligible spend, and its wrapper is in the block's wrapper list.
- Without the block's wrapper list a CAT output is missed, and with it every later output of the same spend group to that scan key.
- A block whose wrapper list holds one asset ID both without and with a revocation hidden puzzle hash lists the wrapper without one first.

**Offers**
- A party to an offer that is paid at a silent payment address finds its payment through the settlement coin at *k* = 0 and its own change at *k* = 1, with the maker paid silently, the taker paid silently, or both.
- A party with two requested payments in one asset, both at silent payment addresses or one of them at another address, asserts one puzzle announcement, over the notarized payment that lists both in the order of its offer.
- The notarized payment of an XCH payment through a settlement coin lists it as (*p*, *amount*, ()), with an empty memo list, and that of a CAT payment as (*p*, *amount*, (*p*)). In both cases the announcement the party asserts is the one the settlement coin creates when every requested payment is rebuilt with its memo list, as the Chia reference wallet does when it takes an offer; an XCH payment listed as (*p*, *amount*) gives a different announcement.

**Compatibility**
- A transaction whose eligible spends are all XCH gives the same spend groups, tweak points and detections with or without the Extension to CATs.
- A scanner without the Extension to CATs finds no payment from a spend group holding both XCH and CAT coins, and a scanner that checks a spend group only against the children of its own coins finds no payment through a settlement coin.

## Future Extensions

### Non-Standard Puzzle Support

Once this CHIP is Final, the set of eligible spends is closed for each address version; for version 0 it is the list given in Eligible CAT Spends. A new kind of eligible spend changes the key sum, and so the spend groups and tweak points, of every transaction that contains one, so old and new scanners would disagree; a new kind of eligible spend therefore needs a new address version. Candidates for later versions are fee CATs ([CHIP-0056](https://github.com/Chia-Network/chips/blob/main/CHIPs/chip-0056.md), not final), NFTs, DIDs and vaults.

Primitives that replace the inner puzzle entirely — such as Chia Vaults, which use MIPS custody puzzles instead of `p2_delegated_puzzle_or_hidden_puzzle` — are not compatible with this approach.

## Security

### ECDH Security

The security of the shared secret relies on the computational Diffie-Hellman (CDH) assumption on the BLS12-381 G1 group. An attacker observing both *A*<sub>syn</sub> (from the puzzle reveal) and *B*<sub>scan</sub> (the recipient's scan public key) cannot compute the shared secret (*input_hash* · *a*<sub>syn</sub>) · *B*<sub>scan</sub> without knowledge of either private key.

### Address Unlinkability

Each payment produces a unique one-time puzzle hash derived from a fresh ECDH shared secret. The input hash ensures unlinkability even when the same sender key is reused across transactions: different coin IDs produce different input hashes, which produce different shared secrets and therefore different one-time puzzle hashes. An observer who does not know the recipient's scan public key cannot determine that two coins were sent to the same recipient. Even an observer who knows the recipient's scan public key cannot link payments without possessing the scan secret key *b*<sub>scan</sub>.

### Unlinkability of Settlement Coin Payments

**The claim.** A destination derived for a payment through a settlement coin (see Payments through Settlement Coins) cannot be tied to the silent payment address it was derived for, or to another destination derived for the same address, by anyone who holds neither the scan secret key nor the secret keys of the deriving party's coins.

**Why it holds.** The destination is the standard puzzle of the one-time key *P* = *B*<sub>spend</sub> + *t* · *G* (plus the label key for change), with *t* a hash of *b*<sub>scan</sub> · *T* and the output index *k*, *T* being the tweak point of the deriving party's spend group. *T* and *B*<sub>scan</sub> = *b*<sub>scan</sub> · *G* are public, and computing *b*<sub>scan</sub> · *T* from them is the computational Diffie-Hellman problem in the BLS12-381 G1 group. With the hash modelled as a random function, *t* is a uniformly random scalar to anyone who cannot compute that point, and *P* is a uniformly random group element that carries no information about the address or about any other destination. This is the standard argument for this construction, the one BIP-352 rests on; it is not a formal proof written for this protocol.

**What is not hidden.**

- The trade itself. A party's coins and the coins it receives are in one transaction, so its proceeds are tied to the coins it spent, as in any offer.
- Amounts, the asset, and the time.
- The counterparty knows which coins it paid for and which it gave.
- A party that derives a destination for someone else's address knows whose it is.
- An offer file shows the destination before the trade settles.

For a party paying itself, a silent destination is no more private on chain than a fresh address of its own wallet. The gain is that the wallet can find the coin again from its silent payment keys alone, and that proceeds can be directed to a third party's published address.

### Scanning Privacy

Only the holder of the recipient's scan secret key *b*<sub>scan</sub> can perform the ECDH computation needed to detect payments. A third party cannot determine whether a coin belongs to a given silent payment address without the scan secret key. Note that compromising the scan key reveals detection capability for ALL past and future payments to that address, but does not allow spending (which requires the separate spend secret key *b*<sub>spend</sub>).

### Omitted Wrapper Lists

A scanner, or a server serving light clients, that leaves a wrapper out of a block's wrapper list misses every CAT output of that asset paid to the scanner in the block and, since scanning stops at the first index with no match, every later output of the same spend group. In the maker-silent offer of Payments through Settlement Coins the CAT payment is at *k* = 0, so the maker's XCH change at *k* = 1 is missed too. The failure is a missed detection, never a false spend, and a recipient can recompute the list from full blocks. The order of the list affects no detection.

Testing every wrapper costs one extra wrap hash per candidate puzzle hash per wrapper. In a survey of mainnet blocks, a CAT wrap hash took 12.76 microseconds on one core (13.04 in a second run), and blocks with tweak points held a mean of 0.45 CAT assets (95th percentile 2, maximum 9) in a recent range and 1.29 (95th percentile 4, maximum 11) in a range one year earlier.

### Sender Privacy

The sender's synthetic public key is visible in the puzzle reveal of their spent coin (for a revocable CAT, in the holder puzzle revealed in the solution). This is inherent to Chia's standard puzzle and is not additional information introduced by this protocol. An observer who can identify the sender's coin can determine that the sender made a transaction, but cannot determine the recipient without the recipient's scan secret key.

### Indistinguishability from Standard Transactions

Silent payment transactions SHOULD be indistinguishable from ordinary Chia wallet transactions on-chain. The anonymity property of silent payments is statistical: an SP one-time puzzle hash is unlinkable from the recipient's address only insofar as the spend bundle producing it cannot be identified as a silent payment in the first place. Any observable signal that flags a transaction as an SP — distinctive multi-input binding patterns, non-standard memo conventions, atypical condition ordering, or any other deviation from wallet output — narrows the candidate set an observer must search to find SP recipients' coins, reducing the effective anonymity set of all SP traffic.

A multi-input silent payment is bound by a cycle of `ASSERT_CONCURRENT_SPEND` conditions, so its anonymity set is the set of transactions that bind their inputs the same way. Wallets that bind multi-coin spends by other means (coin announcements, for example) produce transactions that an observer can rule out as multi-input silent payments.

Implementations MUST:
- Bind multiple input coins only with the `ASSERT_CONCURRENT_SPEND` cycle described in Inputs for Shared Secret Derivation, a pattern that chia-wallet-sdk can also emit for ordinary multi-coin spends.
- Carry no silent-payment-specific data in memos or hints, unless required by a documented extension.
- Construct spend bundles whose condition lists, output ordering, and overall structure are consistent with typical wallet output.

The hint of a CAT output is the hash of the standard puzzle inside its layers, the recipient's inner puzzle hash, which every wallet's CAT payment carries, so it is not silent-payment-specific data.

Wallet conventions change over time. Implementers are encouraged to re-survey them periodically and to keep silent payment transactions matching what ordinary wallets produce.

### Non-Standard Puzzles

Only the three kinds of spend that eligible_spend recognizes are eligible (see Recognizing an Eligible Spend), two of them added by the Extension to CATs (see Eligible CAT Spends). A coin whose puzzle is anything else — a singleton, an NFT, a DID, a vault, a fee CAT, a settlement coin, a CAT inside a CAT, or a revocable CAT spent through the issuer's hidden path — is not an eligible spend. Scanners MUST ignore such spends for grouping, so that every scanner forms the groups the sender formed: they contribute no key, no coin ID, and no concurrent-spend edge. Matching each layer by its exact module hash and the tree hash of the whole puzzle keeps a puzzle that only looks like a CAT layer from being taken for one. A CAT spend that is not eligible still adds its wrapper to the block's wrapper list (see Wrapper List of a Block). Senders MUST NOT rely on such coins for a silent payment's key sum, because no scanner adds their keys (see Inputs for Shared Secret Derivation).

### Key Reuse Across Payments

The input hash mechanism provides defense-in-depth against key reuse. Even though the sender's synthetic key naturally changes with each coin they spend (different coins at different derivation indices produce different synthetic keys), the input hash ensures that even if the same synthetic key were used across multiple transactions, each transaction would produce different one-time addresses because the coin IDs differ.

Within a single transaction, multiple outputs share the same input hash and sender key but derive different one-time addresses via two mechanisms:
- Different recipients have different *B*<sub>scan</sub> values, producing different shared secrets.
- Multiple outputs to the same recipient's scan key use different counter values *k*, producing different tweaks.

### Scan Key Exposure

The scan key *b*<sub>scan</sub> reveals detection capability for all past and future silent payments to the associated address. Compromising it allows an attacker to identify every silent payment the address has received and will receive. It does not allow spending, and — because the keys are derived with hardened derivation — it reveals nothing about the spend key, the master key, or any other key in the wallet, even to someone who also holds the wallet's master public key.

The scan key is therefore suitable for an online device or a watch-only scanner, but its loss is a complete and permanent loss of privacy for the address. Wallets should store it with care.

### Point Validation

Implementations multiply secret scalars by points that come from other parties: the sender multiplies its key sum by the recipient's *B*<sub>scan</sub>, and the scanner multiplies *b*<sub>scan</sub> by sender keys or by tweak points. A point that is on the curve but outside the prime-order subgroup has small order, and a party that can observe which candidate puzzle hash the victim derives from it can learn the victim's secret modulo that order. Repeating this with different points recovers part of the secret.

For this reason, addresses and externally supplied tweak points MUST be validated as described in Silent Payment Address and Tweak Points. Synthetic public keys taken from a block need no separate check by a scanner that deserializes them with subgroup validation, as standard BLS libraries do.

### Collaborative Transactions

The protocol assumes that one party controls every coin in a spend group. A spend group built by several parties would require them to compute the shared secret jointly, and a participant who changes its own coin's conditions after the outputs are derived can make the payment undetectable. There is no security analysis of this setting, and it is not recommended.

An offer is not such a transaction. Each party's spend group holds only that party's coins: a counterparty's coin cannot enter it, because a strongly connected component needs an edge from one of the party's coins, whose conditions the party's signature fixes (sender requirement 6). Each party derives only from its own group (see Payments through Settlement Coins).

## Appendix A: Light Client Support

This appendix is informative.

A "light client" is any Chia wallet that does not process full blocks and does not have a direct connection to a personal full node. Forming spend groups requires executing each spend's puzzle with its solution, which a light client cannot do. A light client instead obtains each block's tweak points (see Tweak Points) and wrapper list from a full node or indexing server, completes the ECDH locally with its scan secret key, and checks the resulting candidate puzzle hashes, bare and under each wrapper of the list, against the block's new coins.

Because the ECDH step happens on the client, the server learns that a client is scanning, but not which address it is scanning for. Tweak points are taken on trust: a server that omits or corrupts one causes a missed detection, but never a false spend, since a spurious match is caught when the derived puzzle hash is checked against the chain. The same holds for the wrapper list: a server that omits a wrapper causes that asset's CAT outputs to be missed and, since scanning stops at the first index with no match, every later output of the same group, but never a false spend.

A server that prunes or filters spend groups for light clients must count among a group's outputs the children of any spend whose puzzle announcement a coin of the group asserts, not only the children of the group's own coins, so that a payment through a settlement coin stays with the party's group; the definition is left to the companion light-wallet proposal.

How tweak points are served — the wire format, how a client checks for matching outputs, pruning of spent groups, and the bandwidth involved — is outside the scope of this CHIP and is left to a separate proposal.
